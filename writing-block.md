# 1. Целевая архитектура

Проект должен использовать централизованную иерархическую архитектуру.

В центре системы находится `BotManager`.

Он выполняет две роли:

1. Управляет жизненным циклом бота и всех его подсистем.
2. Организует взаимодействие между подсистемами через индивидуальные контракты.

Каждая подсистема принадлежит собственному менеджеру.

Менеджеры не знают друг о друге и не обращаются друг к другу напрямую.

Каждый менеджер получает от `BotManager` специальный контракт, предоставляющий только необходимые ему возможности.

## 1.1. Иерархия

```text
Application (index.js)
│
└── BotManager
    │
    ├── InputManager
    │   ├── ChatInput
    │   └── ConsoleInput
    │
    ├── CommandManager
    │   ├── CommandLoader
    │   ├── CommandRegistry
    │   └── Commands
    │
    ├── PerceptionManager
    │   ├── ObservationBus
    │   ├── Detectors
    │   └── Reporters
    │
    ├── StateManager
    │   └── States
    │
    ├── PluginManager
    │   └── Plugins
    │
    └── ServiceManager
        ├── NavigationService
        ├── MiningService
        ├── CraftingService
        ├── InventoryService
        └── MemoryService
```

Это логическая иерархия владения.

Она не означает, что все компоненты должны быть физически вложены в один объект или что необходимо переписать существующие сервисы.

## 1.2. Правила зависимости

Разрешено:

```text
BotManager → AnyManager

AnyManager → собственные компоненты

AnyManager → собственный контракт

BotManager → реализация контрактов
```

Запрещено:

```text
CommandManager → ServiceManager

InputManager → CommandManager

StateManager → PerceptionManager

PluginManager → ServiceManager

ServiceManager → CommandManager
```

Менеджеры не должны импортировать другие менеджеры.

Исключение: BotManager, который знает обо всех подсистемах и координирует их.

Внутренние компоненты одной подсистемы могут взаимодействовать напрямую.

# 2. BotManager — центральный оркестратор

`BotManager` является центральным компонентом всей игровой системы.

Он отвечает за:

- Создание экземпляра Mineflayer.
- Загрузку базовых Mineflayer-плагинов.
- Создание и регистрацию менеджеров.
- Инициализацию подсистем.
- Управление порядком запуска.
- Остановку подсистем.
- Переподключение.
- Выдачу индивидуальных контрактов.
- Координацию взаимодействия между менеджерами.
- Обработку ошибок жизненного цикла.

BotManager НЕ должен:

- Самостоятельно разбирать пользовательские команды.
- Реализовывать алгоритмы добычи ресурсов.
- Реализовывать рецепты крафта.
- Самостоятельно обнаруживать сущностей.
- Форматировать наблюдения.
- Содержать внутреннюю игровую логику сервисов.

Главный принцип:

**BotManager решает, кто, когда и в какой последовательности выполняет работу. Менеджеры решают, как выполняется работа внутри их подсистем.**

## 2.1. Публичные свойства

Предусмотреть удобный доступ к менеджерам внутри самого BotManager:

```js
this.inputs
this.commands
this.perception
this.states
this.plugins
this.services
```

Не использовать глобальные переменные для хранения менеджеров.

Не создавать универсальный Service Locator для внешних компонентов.

# 3. Индивидуальные контракты

Это основное архитектурное изменение.

Каждый менеджер получает собственный контракт взаимодействия с центральным оркестратором.

Контракт должен содержать явные методы.

Пример:

```js
await contract.mine('oak_log', 10)
```

Запрещается заменять их универсальными строковыми запросами:

```js
await contract.request('mining.mine', {
    block: 'oak_log',
    count: 10
})
```

Не использовать универсальные:

```js
request(name, payload)
execute(operation, payload)
dispatch(action)
invoke(method, args)
```

для межсистемных операций.

## 3.1. Размещение контрактов

Создать:

```text
src/core/contracts/
├── InputContract.js
├── CommandContract.js
├── PerceptionContract.js
├── StateContract.js
├── PluginContract.js
└── ServiceContract.js
```

Каждый файл экспортирует функцию создания контракта.

Пример:

```js
export function createCommandContract(botManager) {
    return Object.freeze({
        mine: (block, count) =>
            botManager.services.mine(block, count),

        craft: (item, count) =>
            botManager.services.craft(item, count),

        goto: (position) =>
            botManager.services.goto(position)
    })
}
```

Это пример формы API, а не готовая реализация.

Изучи реальные сигнатуры существующих сервисов и сохрани их корректную работу.

## 3.2. Правила контрактов

1. Контракты создаются центральным оркестратором.
2. Контракт передаётся соответствующему менеджеру при инициализации.
3. Менеджер не получает полный экземпляр `BotManager`.
4. Контракт содержит только необходимые менеджеру методы.
5. Менеджер не получает прямой доступ к другим менеджерам.
6. Реализация контракта может обращаться к нескольким подсистемам.
7. Методы имеют понятные названия и явные параметры.
8. Контракты не должны содержать игровую логику.
9. Контракты не должны самостоятельно создавать менеджеры.
10. Не создавать контрактный метод, если у него нет реального потребителя.

Использовать `Object.freeze()` для защиты публичного набора методов.

Контракт должен содержать методы, которые нужны получающей подсистеме, а не все возможности приложения.

# 4. InputManager

Создать `src/inputs/InputManager.js`.

Этот менеджер полностью владеет системой ввода.

Внутренние компоненты:

```text
InputManager
├── ChatInput
└── ConsoleInput
```

Сохранить существующую модель:

```js
input.start(callback)
input.stop()
```

## 4.1. Обязанности

InputManager отвечает за:

- Создание и регистрацию источников ввода.
- Запуск источников.
- Остановку источников.
- Передачу полученных сообщений через InputContract.
- Корректное освобождение обработчиков событий.

`ChatInput` и `ConsoleInput` должны оставаться независимыми от команд и сервисов.

## 4.2. InputContract

Контракт должен предоставлять возможность передать пользовательский ввод центральному оркестратору.

Предлагаемый метод:

```js
contract.handleInput({
    source: 'chat',
    username,
    message,
    reply
})
```

BotManager принимает этот запрос и передаёт его CommandManager.

InputManager не должен знать, какой менеджер обрабатывает сообщения.

## 4.3. Жизненный цикл

Существующая консоль работает на протяжении всего процесса.

Minecraft Chat привязан к конкретной игровой сессии.

Необходимо сохранить эти правила.

При реконнекте:

- Не создавать вторую консоль.
- Не дублировать обработчики.
- Отключать ChatInput старой сессии.
- Создавать ChatInput новой сессии.
- Продолжать принимать консольные команды.
- Корректно сообщать, если бот ещё не подключён.

Не нарушить обработку Ctrl+C.

# 5. CommandManager

CommandManager становится владельцем всей командной подсистемы.

Он управляет:

```text
CommandManager
├── CommandLoader
├── CommandRegistry
└── Commands
```

Перенести ответственность за загрузку и регистрацию команд внутрь командной подсистемы.

## 5.1. Обязанности

CommandManager отвечает за:

- Загрузку команд.
- Регистрацию команд.
- Разбор пользовательских сообщений.
- Проверку префикса.
- Выбор обработчика.
- Передачу аргументов.
- Обработку ошибок команд.
- Формирование контекста выполнения.

Он не должен:

- Самостоятельно подписываться на Minecraft Chat.
- Читать терминал.
- Импортировать ServiceManager.
- Импортировать конкретные игровые сервисы.
- Управлять PerceptionManager.

## 5.2. CommandContract

Командная подсистема получает индивидуальный контракт с возможностями, необходимыми существующим командам.

Предусмотреть методы для:

```js
contract.goto(...)
contract.follow(...)
contract.stop(...)
contract.mine(...)
contract.chopTree(...)
contract.craft(...)
contract.inventory(...)
contract.equip(...)
```

Также предусмотреть отдельные методы для существующих запросов восприятия:

```js
contract.status()
contract.look()
contract.nearby()
contract.environment()
contract.scan()
```

Сигнатуры определить по существующим командам.

Не изменять пользовательский синтаксис.

## 5.3. Контекст команды

После рефакторинга команды должны получать подготовленный контекст.

Пример:

```js
{
    username,
    args,
    reply,
    contract
}
```

Команды не должны напрямую получать другие менеджеры.

По возможности убрать прямой доступ к Mineflayer из команд.

Если определённая команда зависит от игровых данных, добавить необходимый метод в контракт.

Не создавать универсальный доступ к полному объекту `bot`, поскольку это обходит границу подсистем.

## 5.4. Сохранение поведения

Существующие команды должны продолжать работать:

# 9. Правила координации

Межсистемные операции выполняются через BotManager.

Пример:

```text
ChatInput
   ↓
InputManager
   ↓
InputContract
   ↓
BotManager
   ↓
CommandManager
   ↓
CommandContract
   ↓
BotManager
   ↓
ServiceManager
   ↓
MiningService
   ↓
Mineflayer
```

Путь может выглядеть длинным, но каждый переход имеет конкретную ответственность.

Не оптимизировать этот маршрут путём создания прямых зависимостей между менеджерами.

## 9.1. Асинхронность

Все асинхронные операции должны корректно обрабатывать ошибки.

Использовать `await` при необходимости дождаться результата.

Не создавать необработанные Promise.

Не скрывать ошибки пустыми `catch`.

Ошибки игровых операций должны преобразовываться в ожидаемые результаты там, где это уже предусмотрено сервисами.

## 9.2. Отмена операций

Сохранить существующую функциональность `!stop`.

Не допускать, чтобы рефакторинг нарушил остановку:

- Pathfinder.
- CollectBlock.
- Активной добычи.
- Управляющих состояний движения.

Не реализовывать новый TaskManager в рамках этой задачи.

## 9.3. Жизненный цикл

У каждого менеджера должны быть понятные точки инициализации и очистки.

Необязательно давать всем менеджерам одинаковые методы, если они им не нужны.

Не допускать повторного запуска одной подсистемы при повторном событии.

При реконнекте освобождать ресурсы старой сессии.

Если инициализация одной подсистемы завершилась ошибкой, BotManager должен корректно освободить уже созданные ресурсы.

# 14. Критерии готовности

Рефакторинг считается завершённым, когда:

1. BotManager выступает центральным оркестратором.
2. Подсистемы имеют собственных менеджеров.
3. Менеджеры владеют своими внутренними компонентами.
4. Менеджеры не импортируют друг друга.
5. Межсистемные запросы проходят через индивидуальные контракты.
6. Контракты содержат явные методы, а не строковые операции.
7. Команды не вызывают сервисы напрямую.
8. Система ввода не знает о CommandManager.
9. Сервисная подсистема не зависит от пользовательского интерфейса.
10. Perception сохраняет существующий ObservationBus.
11. Работают подключение, отключение и реконнект.
12. Работают Minecraft Chat и локальная консоль.
13. Не возникает дублирующихся подписок.
14. Все существующие игровые возможности сохранены.
15. Автоматические тесты проходят.
